Why use a shared service for siblings?

Siblings should not depend directly on each other. The store gives them one predictable state boundary: search publishes a term, the list observes orders, and the form observes the selected order.

// Parent-to-child
<app-order-form [selectedOrder]="selectedOrder$ | async">
</app-order-form>

// Child-to-parent event used by this app
@Output() orderSelected = new EventEmitter<Order>();
this.orderSelected.emit(order);

// Parent receives the event and updates shared state
onOrderSelected(order: Order): void {
  this.orderStore.select(order);
}

// Sibling communication used by this app
this.orderStore.search(term);

Containment

The parent template renders the three child selectors, so they appear on the same screen.

Communication

@Input() carries data down. @Output() sends the selected order up. The shared service coordinates the sibling search and form.

Persistence

The Angular service hides HTTP details from components; Spring Boot handles JPA persistence.

Search pipeline

The search control emits values. The store waits for typing to pause, ignores duplicates, cancels stale requests, and shares the latest result with the list.

1Reactive FormControl

OrderSearchComponent exposes a non-nullable searchControl.

readonly searchControl = new FormControl('', {
  nonNullable: true
});
2RxJS input stream

Every value is sent to the shared store.

this.searchControl.valueChanges.subscribe(
  term => this.orderStore.search(term)
);
3Debounce and cancel

Only the latest search is sent to the backend.

debounceTime(250),
distinctUntilChanged(),
switchMap(term => this.orderService.search(term))
4Async pipe renders

The parent binds orders$ and Angular subscribes/unsubscribes through the async pipe.

<app-order-list
  [orders]="(orders$ | async) ?? []">
</app-order-list>

Reactive CRUD form

readonly orderForm = this.formBuilder.nonNullable.group({
  customerName: ['', [Validators.required, Validators.minLength(2)]],
  product: ['', Validators.required],
  quantity: [1, [Validators.required, Validators.min(1)]],
  totalAmount: [0, [Validators.required, Validators.min(0)]],
  status: ['NEW' as OrderStatus, Validators.required]
});

submit(): void {
  if (this.orderForm.invalid) {
    this.orderForm.markAllAsTouched();
    return;
  }
  this.orderStore.save(this.orderForm.getRawValue());
}

End-to-end create flow

The same pattern applies to search, update, and delete. The list uses @Output() to send selection to the parent, the parent updates the RxJS store, and the form uses @Input() selectedOrder before the UI talks to the Angular service and Spring Boot API.

1Angular UI

User submits OrderFormComponent.

2OrderStoreService

Chooses create or update based on whether selectedOrder has an ID.

const request$ = selected?.id
  ? this.orderService.update(selected.id, order)
  : this.orderService.create(order);
3OrderService / HttpClient

POST, PUT, GET, and DELETE requests target the order API.

return this.http.post<Order>(
  'http://localhost:8080/api/orders', order
);
4Spring Boot controller

OrderController maps JSON to Order and delegates persistence to OrderRepository.

@PostMapping
public ResponseEntity<Order> createOrder(
    @RequestBody Order order) {
  return ResponseEntity.status(HttpStatus.CREATED)
      .body(orderRepository.save(order));
}
5Response and refresh

The store selects the saved order and emits refreshSubject, causing orders$ to reload.

tap(savedOrder => {
  this.selectedOrderSubject.next(savedOrder);
  this.refreshSubject.next();
})
